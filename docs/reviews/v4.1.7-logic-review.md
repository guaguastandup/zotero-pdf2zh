## 0. 背景：4.1.6 留下的问题

4.1.6 已经把翻译改成后台任务：

1. 插件 POST `/translate`（以及 `/compare`、`/crop-compare`）。
2. Server **立刻**返回 `{ status: "accepted", taskId }`，HTTP 200。翻译在 daemon 线程里跑。
3. 插件轮询 `GET /api/tasks`，必要时再看 `GET /api/history`，直到该 `taskId` 完成。
4. 完成后 payload 含 `fileList`（文件名）、`filePaths`（Server 本机绝对路径）、`outputDir`。
5. 插件再把 PDF 挂到 Zotero 条目上。

4.1.6 暴露出三类问题，本版要修：

| ID | 现象 | 根因 |
|----|------|------|
| A | Docker / 远程 Server 翻完后条目下没有文件 | 4.1.6 插件**先**用 `outputDir`/`filePaths` 做 `importFromFile`。Docker 的 `outputDir=/app/server/translated` 在 Windows Zotero 里 `PathUtils.join` 抛 `NS_ERROR_FILE_UNRECOGNIZED_PATH`，HTTP 下载走不到。 |
| B | 右键「显示文件所在目录」看到的是 `pdf2zh-1724-ab12cd.pdf`，不是 `xxx.zh-CN.mono.pdf` | 为了躲中文临时文件名，临时文件改成 ASCII；`importFromFile` 默认用源文件 leafName 作为 storage 物理名；`title` 只改条目显示名。 |
| C | 有人没更新插件、Server 自动升级 | 4.0.x 只认 `{ status: "success", fileList }`；4.1.5/4.1.6 已能处理 `accepted`，但三者都不发送协议版本，Server 无法可靠区分。 |

另外：开发者本地用新 Server + 已发布 4.1.6 插件测试时，进度条整段空白，翻完才显示「已导入」。这和 C 的兼容策略有关，见第 3 节。

`/crop` 在 4.1.6 起就是同步 `_success_files_response`，本版没改。

## 1. 挂附件：HTTP 优先，本机路径兜底

### 1.1 4.1.6 行为（有 bug）

顺序：本机 `filePaths` / `PathUtils.join(outputDir, fileName)` → 失败才 HTTP `GET /translatedFile/<urlencoded filename>`。

问题：本机路径在「路径非法」时会抛错，不一定能落到 HTTP；Docker 路径在 Windows 上非法。

### 1.2 本版行为

`fetchAndAttachPDF`：

1. **先 HTTP**：`GET {serverUrl}/translatedFile/{encodeURIComponent(fileName)}`，最多 3 次，间隔 2s。
2. 得到 bytes → 检查开头 1 KiB 内的 `%PDF-` 和末尾 64 KiB 内的 `%%EOF` → `writeTempPdf` 写成 ASCII 临时文件 → `addAttachment`。HTML 错误页或截断 PDF 会进入本机 fallback。
3. HTTP 全部失败后，才遍历 `localPathCandidates(fileName, localPath, outputDir)`：
   - `filePaths[i]`（如果有）
   - `PathUtils.join(outputDir, fileName)`，包在 try/catch 里，非法路径只打日志，不抛到外层。
4. 本机文件存在则 `IOUtils.read` → 同样走 `writeTempPdf` + `addAttachment`（不直接 `importFromFile` 那个可能含中文或 Docker 路径的源文件）。
5. 都失败则抛出 **HTTP 那次的错误**（不是最后一个本机错误）。

`addAttachment` 检查 `attachment?.id`，没有 id 视为失败。

每次 `handleResponse()` 创建局部 `attachKeys = parentId::service::type::safeFileName` 去重，避免 HTTP/本机回退重复挂载；不同任务不会互相清空状态，同一 type 的不同文件名也可共存。

若 Server 返回多个附件，只要其中一个导入失败，整项会报告 partial failure（例如“仅导入 1/2 个附件”），不会因为已有一个附件就发送 `file-done`。

### 1.3 请审查

- HTTP 成功但 `addAttachment` 返回 false（没 id）会进入本机 fallback。只有拿到有效 attachment id 后才记录去重键，避免把失败尝试误判成成功。
- 本机 fallback 读的是 Server 磁盘；插件和 Server 不在同一台机器时应失败并保留 HTTP 错误。逻辑是否正确？
- `encodeURIComponent` 后 Flask/Werkzeug 已解码一次，Server 不再额外 `unquote`，因此字面量 `%2F`、`%20`、`%25` 不会被二次解释。

## 2. 磁盘文件名保持 translated/ 的命名格式

### 2.1 约束

用户要求：Zotero `storage/<KEY>/` 里的 PDF **物理文件名** 应保持 Server `translated/` 的命名格式，例如继续保留原文件名和 `.no_watermark.zh-CN.mono.pdf` 等语义后缀；不要求跨操作系统仍逐字符相同。客户端不允许的字符应按 Zotero 规则安全化。

`Liu 等 - 2026 - ThoughtFold ....no_watermark.zh-CN.mono.pdf`

而不是 `pdf2zh-1724-ab12cd.pdf`。

条目 **title** 仍可按偏好重命名为 `deepseek-mono`（pref `rename=true` 时）。title ≠ 磁盘名。

### 2.2 做法

临时文件继续 ASCII：

```
pdf2zh-{Date.now()}-{random36.slice(2,10)}.pdf
写到 PathUtils.tempDir
```

原因：Windows 上 `PathUtils.join(tempDir, "Shi 等 - test.pdf")` 可能 `NS_ERROR_FILE_UNRECOGNIZED_PATH`。临时名只是中转。

真正定 storage 名。Server 可能运行在 Linux/Docker，而 Zotero 运行在 Windows，因此先使用 Zotero 自己的规则清理跨平台非法字符：

```
requestedLeafName = storageLeafName(fileName) // 去掉路径，保留 xxx.zh-CN.mono.pdf
leafName = Zotero.File.getValidFileName(requestedLeafName) || "translated.pdf"
fileBaseName = leafName 去掉末尾 .pdf          // Zotero API：不含扩展名
importFromFile({
  file: asciiTempPath,
  fileBaseName,
  title: rename ? `${service}-${type}` : leafName,
})
```

不再执行导入后的 `renameAttachmentFile`：`fileBaseName` 已负责设置 storage 文件名，二次重命名既重复，也会让 Zotero 再次通过 `PathUtils.filename` 解析 storage 路径。

`storageLeafName`：空则回落到 `translated.pdf`。`storageFileBaseName` 只 strip 末尾 `.pdf`（大小写不敏感），`foo.zh-CN.mono.pdf` → base `foo.zh-CN.mono`，扩展名来自源临时文件的 `.pdf`。

### 2.3 请审查

- Zotero 7 `importFromFile` 的 `fileBaseName` 是否确实是「无扩展名」？如果某版把它当完整文件名，会变成 `xxx.mono.pdf.pdf`。
- `Zotero.File.getValidFileName` 会按 Zotero 客户端平台清理 `:` `*` 等非法字符；中文、空格、`等` 等合法字符一般保留。跨平台非法文件名不保证与 Server 逐字符一致。
- 临时文件在 `finally` 里 `IOUtils.remove`。若 `importFromFile` 是复制而非移动，删除临时文件安全。若某些环境是 move，会不会删掉 storage 里的文件？按 Zotero 文档 import 是 copy 进 storage。

## 3. 翻译协议：新插件异步，旧插件同步回退

### 3.1 新插件（本版）请求

POST body 在 spread `config` **之后**强制：

```
asyncJob: true
```

Header：

```
X-PDF2zh-Protocol: accepted
X-PDF2zh-Plugin-Version: <package version>
Content-Type: application/json
```

`config` 里没有 `asyncJob` 字段，后写覆盖 spread。

收到响应后：

```
if (status === "accepted" || (taskId && status !== "success"))
  → waitForAcceptedTask(taskId)
else
  → 直接当 success payload 用（兼容旧 Server 同步返回）
```

`waitForAcceptedTask`：最多 3 小时，每 **1 秒** 拉 `/api/tasks`，找不到再拉 `/api/history`。完成判定见 `completedTaskPayload`：

- 失败：`status` 为 `失败`/`failed`，或 `nested.status==error`，或 `finished==true` 且 status 不是 `完成`/`success`。
- 成功：`finished==true` 或 status 为 `完成`/`success`，且 `fileList` 或 `filePaths` 非空。
- 标记完成但还没有文件：最多宽限 20 秒等待元数据可见，之后明确报错，不占用三小时总超时。

任务未完成时回调 `onRunning({ percent, message })`。已去掉 `task.active !== false` 条件，避免 `active` 缺失时不更新进度。

### 3.2 Server 如何决定异步还是同步

`_start_accepted_job` 用于 `/translate`、`/compare`、`/crop-compare`。

判定 `_client_wants_async_job()`（有一个即为异步）：

1. Header `X-PDF2zh-Protocol` ∈ `{accepted, async}`（大小写不敏感）
2. JSON `asyncJob` 在 body 里且为 truthy（`true`/`1`/`yes`/`async`/`accepted`）
3. JSON `clientProtocol` ∈ `{accepted, async}`

**都不满足 → 同步**：在 **当前 Flask 请求线程**里调用 `worker()`，等翻译完，返回：

```
200 { status: "success", fileList, filePaths, outputDir }
或 500 { status: "error", message }
```

并打印：`旧插件协议：同步等待完成后返回 fileList`。

异步：daemon 线程跑 `worker()`，立刻 `200 { status: "accepted", taskId }`。线程内异常：`complete_task(failed)`，返回值丢弃（原 4.1.6 行为）。

`worker()` 结束时仍会 `task_manager.complete_task(..., file_list, file_paths, output_dir, result=payload)`。同步路径把同一个 payload jsonify 回去。旧插件只看 `status`+`fileList`，多出来的字段可忽略。

### 3.3 各客户端实际走到哪条路

| 客户端 | 标记 | 本版 Server 行为 | 进度条 | 长翻译 Windows 长 POST |
|--------|------|------------------|--------|------------------------|
| 4.1.7 插件 | `asyncJob` + protocol/version header | 异步 accepted | 可更新 | 无（POST 立刻返回） |
| 已发布 4.1.5/4.1.6 插件 | 无（但能处理 accepted、会轮询） | **同步**（无法与 4.0.x 区分） | 卡在「正在提交」，翻完跳到已导入 | 可能重新遇到长 POST |
| 4.0.x | 无，只认 success+fileList | 同步 | 旧 UI，本来也没有 running | 和 4.0 一样可能 Network Error |
| 4.1.7 插件 + 旧 4.1.6 Server | 多出来的字段被忽略；Server 仍立刻 accepted | 插件走 waitForAcceptedTask | 正常 | 无 |

**已知权衡：** 4.1.5/4.1.6 插件已经会处理 `accepted`，但不会发 `asyncJob`。本版无法在 POST 时区分它们和 4.0.3。默认未标记=同步，是为了避免 4.0.x 空条目，代价是 **只升 Server、不升插件的 4.1.5/4.1.6 用户** 重新面临长 POST，且看不到中途进度。建议插件和 Server 同时升级。

若把未标记默认改成异步：4.1.6 进度和 Windows 都好，4.0.x 又变空条目。

### 3.4 请审查

- 同步路径占用 Flask 开发 server 的一个线程。多用户同时用旧插件会不会把 Server 卡死？（官方是单用户本机 8890。）
- 同步时 `worker()` 已 `complete_task` 再 jsonify。客户端断开（Windows Network Error）后任务其实已在跑完并 complete。插件重试 POST 会再开一个新 taskId、再翻一遍？旧插件 `retryOperation` MAX_RETRIES=1，翻译请求本身不重试。下载附件会重试。
- 新插件条件 `(taskId && status !== "success")`：若旧 Server 错误响应里碰巧带了 taskId，会不会当成 accepted 去轮询？错误已在前面 `status==error` 被 throw。
- `/api/tasks` 完成后 30 秒从 active 里删掉，插件应能在 history 里找到。轮询 1s，一般没问题。30s 内插件卡住、超过 30s 且 history 匹配失败？`completedTaskPayload` 要求 id 匹配。
- `get_active_tasks_list` 返回 `active_tasks.values()`，含 `taskId`。history 项也有 `taskId`。插件 `taskIdFromPayload` 认 `taskId` 和 `task_id`。
- 新插件 POST 带 `cache: "no-store"`。GET `/api/tasks` 也 `cache: "no-store"`。
- 同步回退是否应该只开在 `/translate`，compare 仍异步？旧插件 compare 同样等 fileList。

## 4. 进度 UI

### 4.1 窗口

Zotero 右下角 `ztoolkit.ProgressWindow`。pref `showProgress` 默认 true。

结构：一行 summary + 每个文件一行。

### 4.2 阶段文案

- submitting：正在提交「file」
- accepted：已提交，正在翻译「file」
- running：正在翻译「file」 · 37% · translate 3/10（percent>0 才显示数字；detail 有则拼上）
- importing：服务器已完成，正在导入附件
- file-done：已导入
- file-failed：失败：message

插件进度条百分比 `jobProgressPercent`（单文件映射到 0–100）：

- submitting 5%
- accepted 12%
- running：12% + 73% × (serverPercent/100)
- importing 90%
- done 100%

summary 行以前用 `done/total`（已导入文件数），翻译中一直是 0%。本版改为：

```
overall = (done + (当前文件未结束 ? fileProgress/100 : 0)) / total * 100
封顶 99，complete() 时 100
running 且 percent>0 时 summary 文本追加 「 · 37%」
```

`changeLine` 之后立刻 `show()`，避免有的 Zotero 版本不刷新文字。

轮询从 3s 改为 1s。

### 4.3 请审查

- 新插件 + 异步 Server：POST 很快返回，应先看到 submitting（读 PDF/上传期间），然后 accepted，然后 running。大 PDF base64 上传期间一直是 submitting。是否可接受？
- 4.1.6 插件 + 本版 Server：整段卡在 submitting（fetch 阻塞），最后 importing → file-done。这是 3.3 的必然结果，不是轮询 bug。
- `show()` 每秒调用会不会让窗口抢焦点、闪烁？
- Server 进度来自解析 pdf2zh_next 终端 `translate 3/10`。解析失败时 percent 一直 0，文案仍有 `正在翻译` 和 `message`（如「正在初始化...」）。
- `completedTaskPayload` 在 `finished==true` 且无文件时返回 null；插件另行记录首次异常完成态，20 秒后失败，不会空等三小时。

## 5. 启动时打印 pdf2zh_next 版本

虚拟环境检查循环：对每个已有引擎 `read_versions(python)`，打印：

```
📦 pdf2zh-next=..., BabelDOC=..., PyMuPDF=..., pypdf=...
```

`pdf2zh_next` 低于 2.9.0 再打警告：**不拦截启动，不拦截普通翻译**。

每个 Server 版本只询问一次是否升级翻译环境（`config/package_update_state.json`）。已 `skipped`/`success`/`declined`/`failed` 则不再问，所以以前启动日志里看不到版本。本版每次启动都打印包版本。

DeepSeek V4 运行时策略（已在 4.1.6，本版未改）：

- 非 `deepseek-v4-*`：不检查 thinking 能力。
- V4 + 运行时支持：把 `--deepseek-thinking-mode` 传给 CLI。
- V4 + 不支持 + thinking=disabled：剥掉思考字段，放行。
- V4 + 不支持 + thinking=enabled：**这一单**在打 API 前 ValueError 停止，避免思考设置被忽略却按思考计费。

### 5.1 请审查

- `read_versions` 是对 conda python 跑一段 importlib 代码，timeout 60s。两个引擎都没有环境时不跑。有环境时启动是否会因此变慢？
- 读版本失败只警告，不 fail 启动。

## 7. 不在本版：Issue #326 json_mode（供对照，不要当成已实现）

设计过、没写代码。原因：拍板后实现优先级转到挂附件 / 文件名 / 旧插件空条目 / 进度条，没有回到 #326。不是技术做不了。

### 7.1 问题

BabelDOC 批量翻译要模型返回 JSON。JSON 失败会 **silent fallback 留原文**，HTTP 仍 success。`xxx_enable_json_mode` 表示「当 BabelDOC 请求 JSON 时带 `response_format: json_object`」。上游默认关，因为很多第三方 OpenAI 兼容接口会 400。

### 7.2 白名单真实含义（和 issue 描述有出入）

`config_map.py` 的 extraData **不是**「拒绝上传未列出的键」。

写 toml 时：

1. 插件 extraData 里非空键 **一律写入** `translator[key]`，并加入 `translator_keys`。
2. 白名单的作用：这次请求 extraData **没带** 的键，如果已在 toml 里，只要它在白名单（或 apiKey/model 映射）中就保留；不在白名单就 `删除旧 key`。

所以：用户每次请求 extraData 都带上 `openai_enable_json_mode=true`，即使不在白名单也会写入。用户只改过 toml、或只在某次带过该键、下次没带，就会被清掉。Issue 里 OpenAI / SiliconFlow 缺白名单项，DeepSeek 已经有 `deepseek_enable_json_mode`。

插件 extraData 值全是字符串。`toml.dump("true")` 会写成带引号字符串，Pydantic 要的是原生 bool。空 = 不设置；`false` 必须写成原生 false，不能省略（省略会被当成不设置，不是关）。

已拍板、未实现：

- 白名单补 `openai_enable_json_mode`、`siliconflow_enable_json_mode`（以及审查其它服务）。
- 编辑器可提供候选下拉，**不预填、不默认打开**（不要像 DeepSeek thinking 那样一开编辑器就插行）。
- Server 写 toml 时按引擎转类型：next 用原生 bool/int；1.x 用字符串。
- json mode 只对 pdf2zh_next 有意义。

| T16 | HTTP 200 返回 HTML 或缺少 `%%EOF` 的截断 PDF | 拒绝下载内容并尝试本机 fallback |
| T17 | 文件名包含字面量 `%2F`、`%20`、`%25` | 下载路由只解码一次，文件名不改变 |
| T18 | `finished=true` 且没有 `fileList/filePaths` | 宽限 20 秒后明确失败 |
| T19 | 两轮任务并发处理同一条目 | 各自使用局部去重 Set，不互相清空或吞附件 |
